# 工作原理

理解四条链路，就理解了整个插件。

## 链路一：公屏（工具门控 + 上下文）

```
玩家: 罗希 在吗
  │
  ├─ AsyncChatEvent / AsyncPlayerChatEvent（MONITOR 优先级）
  │     去重 -> 记进 200 条环形缓冲 -> 命中触发词 -> 去掉触发词
  │
  ├─ POST /mc/message
  │     {mode:"chat", instance, player, op, text, port,
  │      context:"上次触发之后最多 20 条聊天"}
  │     立即返回 {"ok":true}，不等模型
  │
  ├─ 中转转成一条用户消息：
  │     [MC-生存服] 最近的公屏聊天（最多 20 条）：
  │     Alice：去挖矿吗
  │     Bob：好啊
  │     [玩家: Steve] [OP: 否] 现在他说：你怎么看
  │     （这是游戏公屏：只有调用 server_say 工具…）
  │     会话 mc-survive
  │
  ├─ Agent：想说话就调工具 server_say("去啊，挖矿挺有意思的")
  │     工具 -> POST http://127.0.0.1:8900/say
  │
  └─ 插件广播 [NEX AGI] 去啊，挖矿挺有意思的
```

**关键点：模型的正文不会被显示。** Agent 返回的文字只写进中转日志，玩家看不到。所以"不调用工具"就等于"选择沉默"。

### 上下文为什么是 20 条，且从上次触发算起

模型需要知道刚才大家在聊什么，但不需要整天的记录。规则是：

- 缓冲区存 200 条（滚动丢弃最老的）
- 每次触发取"**上一次触发之后**"的消息，最多 20 条
- 上次触发到现在不足 20 条 → 只发这一小段
- 取完把"上次触发位置"推到当前位置，下一次从这里继续

这样连续喊两次不会被同一条消息重复喂，也不会因为服务器冷清而每次都塞 20 条旧话。

## 链路二：`/agi`（独立会话 + 工具回复 + 打字机）

```
玩家: /agi 在吗
  │
  ├─ 回显 [你 -> NEX AGI] 在吗
  ├─ action bar: ✦ thinkink → ✦ thinkink. → ✦ thinkink.. → …（每 0.3 秒长一个点）
  │
  ├─ POST /mc/message {mode:"agi", ...}
  │     立即返回，后台跑
  │
  ├─ 中转：独立会话 mc-survive-dm
  │     （私聊场景：必须调用 mc_agi 工具，player 填 "Steve"…）
  │
  ├─ Agent 调工具 mc_agi(player="Steve", text="在的，怎么了")
  │     工具 -> POST http://127.0.0.1:8900/reply
  │
  ├─ 插件：把这段文字塞进打字机缓冲，action bar 逐字出：
  │     ✦ 在 → ✦ 在的 → ✦ 在的，怎 → …
  │
  └─ 打完 -> action bar 清空 -> 聊天栏 [NEXAGI]= 在的，怎么了（只有他看得到）
```

两个细节：

- `/agi` **必须由工具回复**，和公屏一样"不调用就没人看到"
- 60 秒内没有工具调用就收尾（清掉星星，发一句兜底文案），避免那个星星一直转

### 为什么用 action bar 而不是聊天栏逐字

Minecraft 的聊天栏只能**追加**新行，没法改写已经发出的一行。要在聊天栏"逐字"，只能一行一行刷屏，很脏。

所以：**流式过程放 action bar（可以无限次覆盖同一行），最终结果一次性发到聊天栏。** 这样既有逐字的观感，又不污染聊天记录。

### 为什么是"打字机"而不是"上游给多少显示多少"

工具调用的参数是**一次性到达**的（不是流式 token），所以"上游流式"在这里没意义。插件把整段文字放进缓冲，由主线程按固定节奏放字——无论文字多长、怎么来的，观感都是逐字。

代价是长回答会念得久，所以加了自适应加速：积压超过 40 字时，每 tick 出字量放大到积压量的 1/10。

## 链路三：Agent 发话（`server_say` / `mc_agi`）

```
公屏：
  Agent -> MCP 工具 server_say(text)
        -> 读 ~/.nexagi/mc_ports.json 拿到实例端口
        -> POST http://127.0.0.1:8900/say  {"text": "..."}
        -> 插件主线程广播

私聊：
  Agent -> MCP 工具 mc_agi(player, text)
        -> POST http://127.0.0.1:8900/reply
        -> 插件打字机播完，以 [NEXAGI]= 前缀单独发给那个玩家
```

两个工具都只能发**聊天文字**，没有执行指令的能力。所以"AI 被骗着执行 deop"这件事在架构上不可能发生——最多是它把 `deop xxx` 当聊天内容发出来。

## 链路四：执行服务器指令（`server_command`）

AI 能说话，但不能直接执行指令——需要另一个受控通道：

```
玩家（OP）: 罗希 帮我调成白天
  │
  ├─ 插件记下“最近请求者 = 该玩家，OP=true，时间=现在”
  │
  ├─ Agent 调工具 server_command("time set day")
  │     -> POST http://127.0.0.1:8900/cmd
  │
  ├─ 插件四道门：
  │     1) command-enabled 是否开启
  │     2) 5 分钟内有请求者吗
  │     3) 请求者是 OP 吗
  │     4) 指令首词不在 command-blacklist 里吗
  │
  └─ 全过 -> 以控制台身份 dispatchCommand，控制台记一行 [NEX AGI 执行]
```

几个刻意的设计：

- **不信任调用方**：`server_command` 只有 ``command`` 参数，没有“我是谁”；谁来发由插件自己根据最近请求者判定
- **失败时拒绝**：任何一道门不过都直接返回 `ok:false` + 原因，让模型如实转述给玩家
- **默认黑名单**：`stop / restart / op / deop / ban / ban-ip / kick / whitelist / plugins / reload / execute`，防止一句话把服务器弄崩
- **可一键关闭**：`command-enabled: false`

## 会话划分

| 来源 | 会话 id |
|---|---|
| 公屏 | `mc-<slug>`，如 `mc-survive` |
| `/agi` | `mc-<slug>-dm`，如 `mc-survive-dm` |

两个会话互不影响：`/agi` 里聊的内容不会出现在公屏对话里，反之亦然。

## 为什么同时监听两个聊天事件

Paper 1.19+ 用 `AsyncChatEvent`，旧插件生态还大量用 `AsyncPlayerChatEvent`；装了 TrChat 这类聊天接管插件时，两者可能只触发一个，也可能都触发。

所以插件**两个都听**，并且在 `MONITOR` 优先级（别人 cancel 了也还能收到），再用 `玩家名 + 原文` 做 2.5 秒去重，避免一条消息进两次上下文。

> 这也是唯一一处"魔法数字"：去重窗口 2.5 秒。如果你发现重复，调大它；如果发现连发被吞，调小。

## 系统提示词与工具描述

插件/中转**不发任何 system message**。所有行为约束都写在工具描述里：

- `server_say`：公屏说话 + 无 OP 敏感问题只回「无可奉告」+ 实事求是
- `mc_agi`：私聊说话，其余同上

每条消息末尾还有一句短提醒（"只有调用 xxx 工具玩家才看得到"），因为只靠工具描述，模型偶尔会直接输出正文——那样玩家什么都看不到。
